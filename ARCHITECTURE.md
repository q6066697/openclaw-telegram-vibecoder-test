# Architecture

## Поток запроса

```
┌──────────┐        Telegram Bot API         ┌──────────────────┐
│  Telegram │ ───────────────────────────────▶│  OpenClaw Gateway │
│   user    │◀─────────────────────────────── │   (local, WSL)    │
└──────────┘        polling / send             └─────────┬─────────┘
                                                            │
                                                            │ agent turn
                                                            ▼
                                                  ┌───────────────────┐
                                                  │   OpenClaw Agent   │
                                                  │  (model: gpt-5.4-  │
                                                  │      nano)         │
                                                  └─────────┬─────────┘
                                                            │
                                                            │ HTTPS (via
                                                            │ HTTPS_PROXY)
                                                            ▼
                                          ┌───────────────────────────────┐
                                          │   tinyproxy on VDS (Амстердам) │
                                          │   Basic Auth + IP allowlist    │
                                          └───────────────┬───────────────┘
                                                           │ HTTPS
                                                           ▼
                                                  ┌──────────────────┐
                                                  │   api.openai.com  │
                                                  │   (gpt-5.4-nano)  │
                                                  └──────────────────┘
```

Текстово, по шагам:

1. Пользователь пишет боту в Telegram → Telegram Bot API → OpenClaw Gateway
   (канал `telegram`, режим `polling`, токен из `TELEGRAM_BOT_TOKEN`).
2. Gateway аутентифицирует отправителя: pairing + `commands.ownerAllowFrom`
   (см. [SECURITY.md](SECURITY.md#4-telegram-pairing-и-owner-политика)) —
   решает, кто вправе давать агенту команды.
3. Gateway запускает ход агента (agent turn) с моделью `openai/gpt-5.4-nano`.
4. Агент делает HTTPS-запрос к `api.openai.com`. Процесс OpenClaw настроен с
   `HTTPS_PROXY`, поэтому запрос идёт **не напрямую**, а через tinyproxy на
   VDS в Амстердаме.
5. tinyproxy проверяет Basic Auth и IP отправителя, затем проксирует запрос
   к `api.openai.com` из региона, где OpenAI не возвращает `403 Country not
   supported`.
6. Ответ модели идёт обратно тем же путём: OpenAI → tinyproxy → Gateway →
   Telegram → пользователь.

## Решение про гео-блок: почему точечный HTTP-прокси, а не VPN на устройство

**Проблема.** `api.openai.com` возвращает `403 Country not supported` из
региона разворачивания, при этом Telegram Bot API доступен напрямую без
проблем — это две независимые проблемы с разными причинами, и решать их
нужно было раздельно, не смешивая трафик.

**Рассмотренные варианты:**

| Вариант                          | Плюсы                                   | Минусы |
| --------------------------------- | ---------------------------------------- | ------ |
| VPN на всё устройство/WSL          | Просто, "работает для всего"             | Заворачивает **весь** трафик машины, включая Telegram, npm, ssh и т.д. — избыточный blast radius и лишняя точка отказа для того, что и так работало напрямую |
| VPN только в контейнере/неймспейсе OpenClaw | Изолированнее, чем VPN на устройство   | Больше конфигурации (netns/сетевые правила), сложнее диагностировать, оверхед туннеля для одного HTTPS-эндпоинта |
| **HTTP(S)-прокси (tinyproxy) через `HTTPS_PROXY`** | Затрагивает только процесс OpenClaw и только его исходящие HTTPS-запросы к OpenAI; штатная переменная окружения, которую понимает большинство HTTP-клиентов (в т.ч. используемый OpenClaw) без патчей кода; лёгкий процесс на дешёвом VDS; Basic Auth + IP allowlist ограничивают, кто им пользуется | Нужен отдельный VDS в нужном регионе; защищает только HTTP(S)-трафик (не общий туннель) |

**Выбор:** точечный HTTP-прокси через `HTTPS_PROXY`, ограниченный только
процессом Gateway. Обоснование:

- **Минимальный blast radius** — если прокси или креды скомпрометированы,
  под угрозой только исходящий HTTPS-трафик OpenClaw к OpenAI, а не вся
  сетевая активность машины.
- **Соответствие задаче** — гео-блок стоит только у OpenAI; Telegram уже
  доступен напрямую, туннелировать его незачем.
- **Простота эксплуатации** — `tinyproxy` разворачивается одним
  идемпотентным скриптом ([`scripts/setup-proxy.sh`](scripts/setup-proxy.sh)),
  конфигурация — одна переменная окружения (`HTTPS_PROXY`), без изменений в
  коде OpenClaw.
- **Контролируемый доступ** — Basic Auth и IP allowlist на самом прокси (см.
  [SECURITY.md](SECURITY.md#3-basic-auth-на-прокси)) не дают прокси
  превратиться в открытый релей.

## Компоненты

- **OpenClaw Gateway** — локальный процесс (WSL), режим `gateway.mode: local`,
  auth токен через SecretRef (см. [SECURITY.md](SECURITY.md#2-secretref-для-gateway-токена)).
- **Telegram channel** — polling-режим, токен из `TELEGRAM_BOT_TOKEN`, доступ
  ограничен pairing + owner allowlist.
- **Model provider** — OpenAI `gpt-5.4-nano`, без зависимости от плагина
  `codex` (см. README "Сложности" — эта зависимость роняла Gateway на старте).
- **tinyproxy** — единственная точка обхода гео-блока, живёт вне доверенного
  периметра (внешний VDS), поэтому доступ к нему аутентифицирован и ограничен
  по IP.
